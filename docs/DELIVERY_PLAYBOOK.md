# Delivery playbook — как продавать и доставлять шаблон

Эта инструкция для **тебя как продавца**. Описывает: что входит в продажу, как
обсуждать с клиентом, как доставить за день, чек-листы по нишам, после-продажное
обслуживание.

Если ты ищешь, как настроить YAML — это в [`CUSTOMIZATION.md`](CUSTOMIZATION.md).
Как развернуть в проде — в [`DEPLOY.md`](DEPLOY.md). Архитектура — в
[`ARCHITECTURE.md`](ARCHITECTURE.md).

---

## Что мы продаём

Telegram-бот для приёма и обработки заявок. Один комплект включает:

1. **Бот в Telegram** с понятным меню для клиента (Оставить заявку / Мои заявки /
   Связаться с менеджером / FAQ).
2. **Админ-панель внутри Telegram** для команды клиента — статусы, приоритеты,
   комментарии, назначение, удаление, CSV-выгрузка, статистика дня.
3. **Готовая ниша** (или кастомная под клиента) — формы под услуги клиента,
   тексты статусов под его процесс, FAQ под его вопросы.
4. **Деплой на сервер клиента** — на его VPS или нашем хостинге.
5. **30 дней технической поддержки** после запуска.

### Уже встроено, но выключено по умолчанию

- **Исходящие webhooks** (`WEBHOOK_URLS`) — подписанный JSON на каждое
  событие заявки. CRM-коннектор настраивается на стороне приёмника
  (AmoCRM/Bitrix24/Zapier/Make/n8n) без кода в боте.
- **E-mail уведомления админам** (`SMTP_*`) — простое письмо на каждую
  новую заявку. Любой SMTP (Gmail/Yandex/SendGrid/Mailgun).

### Что НЕ входит (нужны допы)

- Двусторонняя интеграция с CRM клиента (создание задач из бота → синхронный
  ответ обратно). Однонаправленный webhook работает «из коробки».
- Кастомные доработки за рамками YAML.
- SMS-уведомления — нужна обвязка SMS-провайдера, отдельный модуль.
- Веб-форма для подачи заявок «в обход бота».
- Аналитика «по конверсиям» — есть только дневная статистика.

## Workflow продажи: от созвона до запуска

### Шаг 0 — квалификация (5–15 минут)

Не каждому клиенту нужен этот бот. Подходит, если:
- ✅ У клиента есть **поток входящих заявок** (хотя бы 10 в день).
- ✅ Заявки обрабатываются **человеком** (а не сразу делается работа).
- ✅ Заявка имеет **несколько полей** (телефона мало).
- ✅ У клиента **уже есть Telegram-канал** или активная аудитория там.

Если бот нужен «для красоты» и заявок 2 в неделю — лучше отказаться, не окупится.

### Шаг 1 — техзадание (15–30 минут)

Это самый важный шаг. Заполни с клиентом базовый бриф (есть шаблон ниже).
**Цель — получить полный YAML-контент за час**, не за неделю.

#### Бриф (можно копировать в чат)

```
1. Название компании и ника менеджера в Telegram:
2. Телефон менеджера + рабочие часы:
3. Один абзац: что вы делаете, для кого, чем уникальны:
4. Какие услуги/категории должны быть в боте (3–6 штук)?
   Для каждой:
   - Название (с эмодзи)
   - 2–5 вопросов, которые нужно задать клиенту
5. 5–8 частых вопросов клиентов + готовые ответы:
6. Как у вас называются статусы заявки?
   («Новая → Связались → В работе → Завершена» или иначе?)
7. Telegram-ID админов (@userinfobot подскажет):
8. Где будет деплой: ваш сервер или мой хостинг?
9. Когда планируете запуск?
```

Если клиент не отвечает на какой-то пункт — используй дефолты из ближайшей
ниши. Не бойся показывать готовые ниши на созвоне: «у нас уже есть аналог —
вот его кнопки, вам подойдёт?». Часто клиент скажет «да, только три кнопки
переименуйте».

### Шаг 2 — настройка профиля (1–2 часа)

```bash
# Клонируешь самую близкую нишу (см. таблицу ниже)
make new-client SLUG=<client_slug>_<niche> PROFILE=auto_service
# Редактируешь 5 YAML по брифу
make validate-profile PROFILE=<client_slug>_<niche>
```

После этого профиль готов — можно показать клиенту локально или сразу деплоить.

### Шаг 3 — деплой (30 минут)

Подробности в [`DEPLOY.md`](DEPLOY.md). Короткий путь:

```bash
# На сервере клиента (или твоём)
git clone <твой fork шаблона> /opt/leadbot && cd /opt/leadbot
cp .env.example .env
# Прописать BOT_TOKEN, ADMIN_IDS, POSTGRES_PASSWORD, CONTENT_PROFILE
make prod-up
```

Проверь, что:
- ✅ Бот отвечает на `/start`
- ✅ Заявка проходит до подтверждения и сохраняется
- ✅ Админ видит её через `/admin` и может изменить статус
- ✅ Уведомление о новой заявке приходит в личку или группу менеджеров

### Шаг 4 — обучение менеджера (15–30 минут, видео-созвон)

Покажи менеджеру клиента:
1. Как открыть `/admin` и какие там фильтры.
2. Как менять статус (включая обязательную причину для «Отклонена»).
3. Как писать внутренний комментарий vs клиенту.
4. Как назначить заявку на конкретного админа.
5. Как удалить ошибочную заявку (soft-delete, не сразу из БД).
6. Как выгрузить CSV.

Запиши экран — повторишь это ещё много раз для разных клиентов.

### Шаг 5 — передача (15 минут)

Дай клиенту:
- Ссылку на бота (`t.me/<bot_username>`).
- Полный список их админов (имя + Telegram ID) — чтобы они проверили доступ.
- Контакт «как связаться по поддержке» (на 30 дней).
- Запись обучения менеджера (если делал).

### Шаг 6 — обслуживание (30 дней)

Что входит в support-период:
- Правка опечаток в YAML по запросу клиента.
- Помощь с восстановлением доступа админа.
- Помощь с пониманием статистики.
- Откат к предыдущему деплою при критическом баге (см. ниже про updates).

Что НЕ входит:
- Новые категории / новые поля.
- Изменение логики статусов.
- Интеграции с CRM.
- (Это всё — отдельные платные доработки.)

## Чек-листы по нишам

### 🔧 Автосервис (`auto_service`)

**Подходит для:** автосервисы, шиномонтаж, СТО, тюнинг-ателье, выездной шиномонтаж.

**Что обычно правится в YAML:**
- `brand.yaml` — название сервиса, телефон, рабочие часы.
- `categories.yaml` — оставить нужные категории (ТО, ремонт, шиномонтаж,
  кузовной). Удалить «кузовной», если сервис только моторный.
- В каждой категории — поправить варианты в полях типа `choice`
  (бренды масел, размеры колёс, актуальные именно для этого сервиса).
- `texts.yaml` close_reasons — добавить пункты типа «На запчасти ждать неделю»,
  «Клиент уехал к конкуренту».

**Типичные вопросы клиента:**
- «А если у клиента машины нет — он просто оставил телефон?» — Категория
  `other`, она требует только описание.
- «Можно сразу записать на дату?» — Да, `preferred_date` уже есть в ТО и
  шиномонтаже.
- «Можно ли добавить услугу автомойки?» — Добавь новую категорию в
  `categories.yaml`, перезапусти `make seed`.

**Время на ввод в эксплуатацию:** 2–4 часа.

### 💅 Салон красоты (`beauty_salon`)

**Подходит для:** парикмахерские, ногтевые студии, барбершопы, массажные кабинеты, SPA.

**Что обычно правится:**
- `brand.yaml` — название студии, инстаграм-ник менеджера.
- В категории «Волосы» — варианты услуг (некоторые салоны не делают окрашивание,
  некоторые только барбер-стрижки).
- Добавь «Любимый мастер» в нужные категории (у тебя уже есть в «Волосах»).
- `texts.yaml` statuses → «Записан» обычно лучше чем «В работе» (для салона
  «работа» = пока клиент в кресле).

**Типичные вопросы клиента:**
- «Как клиент пришлёт фото референса?» — Wizard step «Файлы» работает в любой
  категории; поясни в FAQ.
- «Можно показывать свободные слоты?» — Нет (нужен календарь, отдельный
  модуль). Сейчас клиент пишет желаемую дату, мастер подтверждает.
- «Можно автонапоминание за день?» — Нужен планировщик, отдельный модуль.

**Время на ввод в эксплуатацию:** 2–3 часа.

### 🏥 Медцентр / клиника (`medical_clinic`)

**Подходит для:** частные клиники, кабинеты УЗИ, лаборатории, врачебные кабинеты.

**Что обычно правится:**
- Список специалистов в `categories.yaml: appointment.questions.specialist`.
- Список исследований в `ultrasound.questions.study_kind`.
- `brand.yaml` — обязательно правильное название клиники и лицензионная
  фраза в `welcome_intro` (мед.деятельность регулируется).

**ВАЖНО для медицины:**
- Бот собирает **персональные данные** (ФИО, год рождения, симптомы) — клиент
  обязан иметь оформленное согласие на обработку (152-ФЗ). Согласие даётся
  отдельно (на сайте / при первом визите). Это **не наша зона** — упомянуть
  на созвоне.
- Не показывай в FAQ обещание «приём в течение часа», если клиент не готов
  это обеспечить — лучше «свяжемся в течение 30 минут».
- Желательно поставить более жёсткий `max_leads_per_10_minutes` (сейчас 5)
  в `config.yaml` — медцентры чаще атакуют боты-генераторы.

**Типичные вопросы клиента:**
- «Можно ли отправлять результаты анализов через бота?» — нужна авторизация
  и защищённый канал отдачи, отдельный модуль. Сейчас — нет.
- «А вызов скорой?» — НЕТ. Бот не для скорой — пиши в FAQ явно
  «при угрозе жизни звоните 103».

**Время на ввод в эксплуатацию:** 3–5 часов (больше согласований).

### 🎯 Generic (`default`)

**Подходит для:** IT-агентства, фриланс-команды, дизайн-студии, консалтеры —
всё, где «приходит запрос → менеджер созванивается → договариваются».

**Что правится:** всё с нуля под клиента. Эта ниша — самая нейтральная;
используй её, если ни одна из 3 готовых не близка.

**Время на ввод в эксплуатацию:** 4–8 часов.

## Чек-лист «готово к запуску»

Перед тем как сказать клиенту «запускаем»:

- [ ] `make validate-profile PROFILE=<client>` — без ошибок.
- [ ] `make test` — все тесты pass.
- [ ] В YAML проверены:
    - [ ] `brand.company_name` совпадает с фактическим названием.
    - [ ] `manager_username` и `manager_phone` — корректные.
    - [ ] Все категории показывают релевантные клиенту услуги.
    - [ ] FAQ покрывает 5–8 самых частых пре-сейл вопросов.
    - [ ] Все `close_reasons` — на языке менеджера клиента.
    - [ ] `eta_response_hours` реалистичен.
- [ ] Боту установлены аватарка, описание (`/setdescription`, `/setuserpic` у
  @BotFather) — это часть фирстиля.
- [ ] `BOT_TOKEN`, `ADMIN_IDS`, `POSTGRES_PASSWORD` уникальны для этого
  деплоя (не дефолтные из `.env.example`).
- [ ] На сервере настроен ежедневный бэкап PostgreSQL (см. `DEPLOY.md`).
- [ ] Заявка протестирована end-to-end: клиент → форма → файл → подтверждение
  → админ видит → меняет статус → клиент получает уведомление.

## Развёртывание обновлений шаблона у клиента

Когда ты улучшаешь шаблон (новая фича, баг-фикс) — клиенты тоже хотят это
получить. План:

```bash
# На сервере клиента
cd /opt/leadbot
git fetch upstream             # upstream = твой основной репозиторий
git merge upstream/main
# Клиент-специфичный профиль остаётся в app/bot/content/<client>/ нетронутым.
make prod-migrate              # alembic upgrade head — если новые миграции
docker compose -f docker-compose.prod.yml build
make prod-up
```

**Если конфликт в YAML** (ты в default/ что-то поменял, и клиент тоже у себя):
- Default-профиль не подключён к клиенту, конфликта не будет.
- Если клиент сам форкнул default, попроси использовать `make new-client`
  с собственным slug — обновления не будут затрагивать его профиль.

**Откат**:
```bash
git reset --hard <last-known-good-tag>
docker compose -f docker-compose.prod.yml build
make prod-up
make prod-migrate              # ВНИМАНИЕ: миграции вниз не всегда автоматизированы — проверь!
```

Перед серьёзными обновлениями (новая миграция) — сначала бэкап БД.

## Цена ошибки

Этот шаблон обрабатывает заявки клиента — упавший бот = потерянные продажи.
Поэтому:

- ❌ Не делай «горячие» правки YAML прямо на проде без git-коммита.
- ❌ Не запускай миграции без бэкапа.
- ❌ Не давай `ADMIN_API_TOKEN` посторонним — он позволяет читать все заявки
  через REST API.
- ✅ Проверяй каждый деплой `/start` сразу после `make prod-up`.
- ✅ Подпиши `/healthz` на UptimeRobot (бесплатно) — узнаешь о падении за
  пару минут.

## FAQ продавца

**В чём отличие от заказной разработки?**
Скорость и цена. Кастомный бот = 200k+ ₽ и 3 месяца. Этот шаблон под нишу =
0.5–1 день работы и предсказуемая цена.

**Что если клиент попросит фичу, которой нет?**
Три ответа:
1. Заведи себе бэклог. Если 3 разных клиента просят одно и то же — реализуй
   и продай всем как обновление.
2. Дороже — отдельная доработка за плату по тарифу Custom/Branded.
3. Если фича вне домена (магазин, расписания, оплата) — отказывай мягко.

**Можно ли продавать как SaaS?**
Текущая архитектура — single-tenant (один деплой на клиента). Multi-tenant
SaaS — это переписать минимум БД и middleware. См. `DEPLOY.md` секцию
"Scaling considerations". Простая модель: один VPS на клиента = простая
поддержка + понятный счёт.

**Как считать стоимость одного клиента?**
- VPS (1 vCPU/2 GB) ≈ 300–500 ₽/мес.
- Твой support ≈ 1 час/мес после первых 30 дней.
- Bot-token и Telegram-доставка — бесплатно.
- Итого abonement: 1500–3000 ₽/мес после внедрения — типичная цена.

## Что уже в шаблоне сверх базы

- **Soft-delete заявок** с журналом событий.
- **Редактирование ответов** на confirm-экране (по одному, без перепрохода).
- **Альбомы файлов** — debounce на отправку, чтобы 10 фото = 1 экран.
- **Кнопка «📎 Показать файлы»** в админ-карточке — отдаёт все вложения
  альбомом.
- **Исходящие webhooks** на `lead.created`/`lead.status_changed`/`lead.deleted`
  с HMAC-SHA256 подписью.
- **SMTP-уведомления** админам на каждую новую заявку.
- **REST-эндпоинты** `/admin/*` для интеграций (Bearer-токен).

## Что в следующих тирах (на доработку)

- **Двусторонняя CRM-интеграция** (AmoCRM/Bitrix24) — сейчас односторонний
  webhook; обратная синхронизация требует CRM-специфичного коннектора.
- **Календарь / онлайн-запись** — клиент выбирает слот, бот блокирует время
  у мастера.
- **AI-ассистент** на типовые вопросы (FAQ-bot поверх Claude API).
- **Аналитика по конверсиям** — воронка от первого `/start` до закрытой
  заявки.
- **SMS-уведомления** — обвязка SMS-провайдера (SMS.ru, SMSC).

Эти модули — **расширение твоего продуктового каталога**, не обязательные
улучшения. Включай в продажу то, что клиенту действительно нужно.
